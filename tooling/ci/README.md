# @ai-sdlc/ci

Two scripts.

**`ci:local [--sha <ref>] [--allow-unknown] [--no-status] [--container]`** tests a snapshot of a commit (a shared clone in its own `.ci-local/run-<sha>-<random>/`), runs the CI steps in a scrubbed environment, and posts a commit status.

- **The CI definition is the integration branch's, not the commit's.** The steps are read from `sdlc.config.json` as committed on `origin/<integration>` (`loadConfigAt`), never from the snapshot, so a branch cannot change what its own gate runs. A commit that changes the file is warned that the change takes effect only after it lands. When `origin/<integration>` has no `sdlc.config.json` yet (the first commit), the working tree's is used, and the run says so. A base config that does not validate fails the run.
- **`--container`** runs install and every step inside `ci.container.image` (docker by default, or `engine: "podman"`): `<engine> run --rm [--network <n>] -v <snapshot>:/work -w /work -e NAME… <image> sh -c '<step>'`. Only the snapshot is mounted; no home directory, no env file. The scrubbed variables pass by name, with their values in the engine client's environment rather than on the command line. An engine that is not installed, no `ci.container` declared, or a container that does not start (exit 125) is could-not-run, which holds the verdict. The steps are still the branch's code; the container is what keeps that code off this machine's credentials. The snapshot is a plain local clone in this mode, since a `--shared` clone's object store is a host path, and the image is part of the cache key.

- **Content checks are cached; history checks are not.** A pass is remembered as `.ci-local/passed/<key>`, written atomically, where the key is sha256 of the tree id, the resolved CI steps, the Node and pnpm versions, platform and arch, the lockfile hash and `ci-local.mts`'s own source. Change any of them and the content checks run again. History checks read a commit range that a tree id says nothing about, so they run on every invocation, cache hit included: steps named in `HISTORY_STEPS` (`trailers`), any step whose command passes `--range`, and any step carrying `history: true`. On a hit they run without `pnpm install`, so they must need only node and git.
- **One run per SHA at a time.** `.ci-local/locks/<sha>.lock` is created exclusively and holds the pid and start time. A second run waits, then usually hits the cache. A lock whose pid is not running is taken over, and the run says so. A run removes only its own snapshot, and only on a pass; a failed one is kept for inspection.
- **Status contexts.** `local-ci` is posted `success` only for a real pass, `failure` on a fail, and `error` for a held unknown. An `--allow-unknown` override posts `success` under **`local-ci/allow-unknown`** and leaves `local-ci` unset, so anything requiring `local-ci` does not accept an override.

**`land [--allow-unknown]`** performs the landing procedure (`.agents/skills/git-workflow-and-versioning/landing.md`) deterministically, so an agent needs no raw push or merge permission. It refuses the integration, staging or production branch, a detached HEAD and a dirty tree. It fetches, then refuses unless `origin/<integration>` is an ancestor of HEAD. It requires a `Progress:` or `No-Item:` trailer across the range (the guards' `trailers --range`). A branch touching `docs/requirements/` must touch nothing else, unless it is the `x-000-*` discovery branch. It then pushes (never forced) and runs `ci:local` on the pushed SHA. It finds or creates the PR into the integration branch, with a body listing the Progress/Closes/No-Item lines. It re-checks that the PR head is the tested SHA and that `origin/<integration>` has not moved. It merges with a merge commit (never a squash), with `--delete-branch` only when a commit carries `Closes:`, and finally runs `ci:local --sha origin/<integration>` to give the merge commit its status. One line per step. Exit 0 landed, 1 refused or failed, 2 could not ask.

The project's own: it arrives with `ai-sdlc init`, and is changed here when the project needs it. `pnpm sdlc diff base` shows what changed upstream; `pnpm sdlc update base` takes it without overwriting a local edit (docs/kit/registry.md).
